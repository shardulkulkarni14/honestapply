# Account auto-signup (apply stage)

Some ATS portals (SAP SuccessFactors, Haufe Umantis, …) require a **registered
account** before you can apply — there's no guest-apply path. By default
honestapply routes those jobs to `needs_human`. With account-signup **enabled**,
the apply agent instead **creates the account itself** (email + a managed
password) and verifies via Gmail, then applies — behind the same safety guards.

It's **opt-in and off by default.**

## The key guarantee: the agent never sees the password

Passwords are generated by honestapply and stored in a local vault; they are
**never readable by the LLM agent, never printed, never logged, never committed.**

- **Generation + storage** (`honestapply.vault`): a strong random password per
  site, kept in the **OS keyring** (macOS Keychain / Windows Credential Manager /
  Linux Secret Service) or, on headless/CI, a **Fernet-encrypted file**.
- **Injection** (`honestapply.secret_proxy`): during signup the browser runs
  through a proxy. The agent types the literal placeholder `{{honestapply_password}}`;
  the proxy swaps in the real value *at the page* and **redacts it on the way back**,
  so the agent can't read it via `browser_evaluate` either.

So the plaintext lives only in the vault and in memory at the moment of injection.

## Enable it

1. Install the extra (OS keyring + encryption):
   ```bash
   pip install -e ".[accounts]"
   ```
2. Turn it on in `.env` (or the environment):
   ```bash
   HONESTAPPLY_ENABLE_ACCOUNT_SIGNUP=true
   ```
3. (Headless/CI only) choose the encrypted-file vault and supply a key:
   ```bash
   HONESTAPPLY_VAULT_BACKEND=file
   HONESTAPPLY_VAULT_KEY=<a Fernet key>   # else a 0600 key file is generated
   ```
4. Check it:
   ```bash
   honestapply doctor        # shows "Account signup: ENABLED · vault: keyring · N saved account(s)"
   ```

The account is created under the email in `config/profile.json`. For email
verification to work, that email must be the one your connected Gmail receives
(see `docs/GMAIL_SETUP.md`).

## Run

Nothing new — the normal apply flow now handles account-walled jobs instead of
skipping them:

```bash
honestapply apply --dry-run     # first runs are dry-run; account IS created to reach the form
honestapply apply               # real submissions (confirm first — these go out under your name)
```

> Note: even a **dry run** will create the portal account, because the account is
> needed to *reach* the application form. Dry-run still means the final **Submit**
> is not clicked. CAPTCHAs still route to `needs_human`.

## Manage saved credentials

Passwords are never shown — only site names/metadata:

```bash
honestapply accounts list                 # sites, emails, created/last-used
honestapply accounts rotate <site>        # replace with a fresh password
honestapply accounts delete <site>        # forget a site's credentials
```

## Safety recap

- Opt-in (off by default); account-walled jobs still go to `needs_human` unless enabled.
- The agent never sees/prints/logs the password; it's vault-stored and proxy-injected.
- Dry-run-first, per-day and per-employer caps, and CAPTCHA→needs_human all still apply.
- The agent only types the password into a site's own password fields, nowhere else.
